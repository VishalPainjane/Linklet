# Shortcake — Complete URL Shortener Engineering Blueprint

**Document status:** Updated baseline / source of truth  
**Revision:** 2.0  
**Last reviewed:** 10 November 2026  
**Project name:** Shortcake  
**Product:** URL shortener and systems-engineering laboratory  

> A tiny link, backed by serious engineering.

This document replaces the earlier TypeScript/Express/Cloudflare blueprint. The approved backend is now **Python + FastAPI**, the frontend is **Next.js**, Python dependencies are managed with **uv**, persistence uses **PostgreSQL through SQLAlchemy's async ORM**, caching uses **Redis**, and performance testing uses **Locust**.

# 0. Executive decisions

## 0.1 What we are building

Shortcake is a production-minded URL-shortening application and a practical laboratory for studying backend and distributed-systems engineering. We will not stop at a create/read/delete API. We will implement and measure:

- Secure random short-code generation and collision handling.
- Simultaneous URL creation by many users.
- Custom-alias conflicts and idempotent request retries.
- PostgreSQL schema design, ORM behavior, SQL, indexes, transactions, MVCC, locks, isolation and connection pools.
- Redis cache-aside behavior, TTL, eviction, invalidation, hot keys and cache stampedes.
- FastAPI/asyncio request concurrency, Uvicorn workers, HTTP connections, timeouts and backpressure.
- RabbitMQ exchanges, queues, acknowledgements, publisher confirms, retries, dead-letter queues and idempotent consumers.
- Docker images, containers, volumes, networks, resource limits and reproducible development.
- Load testing with Locust, including distributed load generation and tail-latency analysis.
- Deployment, free-tier limits, secrets, failure handling and recovery.

The project will be implemented incrementally. We will not add every dependency on the first day.

### Why SQLAlchemy instead of SQLModel?

We will use **SQLAlchemy 2.x directly**. SQLModel is built on SQLAlchemy and Pydantic and is a good option for simple FastAPI projects, but SQLAlchemy gives us more direct control over ORM behavior, Core statements, transactions, session lifetimes, indexes and performance experiments. We can still use Pydantic schemas at the API boundary.

Using an ORM does not mean avoiding SQL. We will use SQLAlchemy ORM for normal application operations and SQLAlchemy Core / parameterized SQL for operations such as `INSERT ... ON CONFLICT`, aggregation and database-specific optimizations. We will inspect the SQL generated by the ORM.

### Why uv?

uv will manage the backend's Python version constraint, `.venv`, `pyproject.toml`, dependency groups and committed `uv.lock`. It is fast, provides reproducible lock-based installs and is supported by Render's Python deployment workflow when the lockfile is present.

- Kubernetes, Docker Swarm, cluster orchestration and service meshes.
- Application clustering/autoscaling as an initial deployment feature.
- OpenTelemetry and centralized instrumentation.
- Prometheus and Grafana.
- Playwright and browser automation.
- Kafka/Redpanda in the first version.
- ClickHouse in the first version.

Docker and Docker Compose remain in scope for local containerization. Locust master/worker mode is allowed for distributing load generation; it is not application orchestration or Kubernetes.

# 1. Product requirements and behavior

## 1.1 Core product features

The first useful release supports:

1. Create a short URL with a generated code.
2. Create a short URL with a user-selected custom alias.
3. Resolve a short code and redirect to its destination.
4. Optional expiration timestamp.
5. Disable a link.
6. List and inspect owned links after authentication is introduced.
7. View aggregate click statistics after the queue/analytics phase.
8. Rate-limit abuse-prone operations.

Authentication can be implemented after the core redirect and persistence path works. The data model reserves ownership fields so authentication does not require redesigning the URL table.

## 1.2 Duplicate original URLs

**Default policy: identical destination URLs submitted by different users create independent short links.**

For example, User A and User B can both shorten `https://example.com/article`, but each receives a different code. Their analytics, ownership, expiration and disabled state remain independent. We will not apply global destination deduplication.

A later optional rule may deduplicate within one authenticated account. This must be an explicit product choice, not an accidental side effect of a unique constraint on `destination_url`.

## 1.3 Custom aliases

A custom alias is globally unique. If two users concurrently claim `docs`, exactly one insert succeeds. The other receives `409 Conflict`. PostgreSQL's unique constraint is the final arbiter; an application-level `SELECT`-then-`INSERT` check is insufficient under concurrency.

## 1.4 Initial workload hypothesis

Start performance experiments with:

- 99% redirects/lookups and 1% URL creation.
- A uniform code distribution for baseline measurements.
- A hot-key / Zipf-like distribution where a small fraction of URLs receive most requests.
- Separate read-only, write-only and mixed workloads.

The 99:1 distribution is an initial synthetic assumption. We will vary it and document each workload.

## 1.5 Success criteria

Do not claim that the service handles a particular RPS until a repeatable test demonstrates it. Every benchmark records:

- Offered/requested load and completed throughput (RPS).
- p50, p95 and p99 latency, plus maximum latency.
- HTTP status counts, failures and timeouts.
- Application CPU, RSS memory and process count.
- Database query latency, active connections and connection-pool wait time.
- Redis hit ratio, command latency and command count.
- RabbitMQ publish/consume rate, unacknowledged messages and queue depth.
- Locust worker CPU/RAM/network use, so a load-generator bottleneck is not mistaken for an application bottleneck.

We are not adding Prometheus/Grafana/OpenTelemetry. Locust reports load-test statistics; `docker stats`, PostgreSQL views, Redis `INFO`/`SLOWLOG`, RabbitMQ's management UI and ordinary structured logs are sufficient for the initial lab.

## 2.3 Request flows

### URL creation

1. Client sends `POST /api/v1/urls`.
2. FastAPI validates the body with a Pydantic schema.
3. Service validates/normalizes the destination and checks any idempotency key.
4. For generated codes, `secrets` creates a cryptographically random Base62 candidate.
5. SQLAlchemy executes an insert with `ON CONFLICT DO NOTHING RETURNING`.
6. If the candidate collides, the service generates another code and retries a bounded number of times.
7. PostgreSQL commits the URL record.
8. API returns the short URL and metadata.

### Redirect

1. Browser requests `GET /{code}`.
2. FastAPI validates the code's allowed syntax.
3. Application checks Redis key `url:{code}`.
4. Cache hit: validate expiry/disabled fields and return 302.
5. Cache miss: query PostgreSQL using the code primary key.
6. Unknown code returns 404; disabled/expired code returns 410.
7. Active result is cached with a bounded TTL and returned as 302.
8. Click event is queued asynchronously according to the selected delivery mode. The redirect must not wait indefinitely for analytics.

### Click analytics

1. Redirect handler creates a small event with a unique `event_id`.
2. A bounded publisher path sends it to RabbitMQ.
3. Consumer validates the event and starts a DB transaction.
4. Consumer inserts `event_id` into `processed_events`.
5. Only a newly inserted event increments the corresponding `url_stats` row.
6. Consumer acknowledges the broker message only after the database transaction commits.

# 3. Technology details and responsibilities

## 3.1 FastAPI

FastAPI is responsible for HTTP routing, dependency injection, request parsing, validation integration, response serialization and OpenAPI documentation. Keep route functions thin; route handlers should call service functions rather than contain all business logic.

Use `async def` routes for asynchronous SQLAlchemy, Redis and RabbitMQ operations. Do not call blocking database clients or long CPU-heavy functions from the event loop. If CPU-heavy work is ever introduced, measure it first and move it to an appropriate thread/process worker.

## 3.2 Pydantic v2

Use separate schemas for incoming requests and outgoing responses. Do not return ORM objects directly without an explicit response schema. Configure ORM attribute reading where appropriate, and use explicit serialization for fields such as timestamps and URL strings.

`pydantic-settings` reads environment variables into a typed settings object. Secrets must never be checked into source control.

## 3.3 SQLAlchemy 2.x async ORM

Use:

- `DeclarativeBase` and `Mapped[...]` model declarations.
- `create_async_engine()`.
- `async_sessionmaker()`.
- One `AsyncSession` per HTTP request or independent background task.
- `async with session.begin()` for explicit transactional boundaries.
- SQLAlchemy PostgreSQL `insert()` for conflict-safe inserts.
- SQLAlchemy Core or `text()` for special queries where it improves clarity/performance.

**Never share one `AsyncSession` among concurrent asyncio tasks.** An `AsyncSession` represents mutable transaction state and is not safe for simultaneous use by independent tasks. Give each request/consumer task its own session. This is a critical concurrency rule.

## 3.4 Alembic

Alembic is the only schema migration mechanism. Do not run `Base.metadata.create_all()` in production application startup. Generate/review migrations, apply them explicitly and record the migration revision.

Use a direct PostgreSQL connection for migrations when a provider's transaction pooler is unsuitable for DDL/session-level operations. The app can use a pooled connection.

## 3.5 Redis

Redis is the shared read cache and rate-limit store. Use Python's `redis.asyncio` API with one long-lived client/pool per process. Do not create a new Redis TCP connection per request.

We will also implement a small process-local LRU cache from scratch as a learning experiment, but Redis remains the actual shared cache for multi-process correctness/performance tests.

## 3.6 RabbitMQ

Use RabbitMQ as a work queue for asynchronous click-event processing. Use `aio-pika` for asynchronous connections, publisher confirms and consumers. Local broker is Dockerized. CloudAMQP may be used for a small deployed demo, subject to its current free-plan limitations.

## 3.7 Locust

Locust is the primary load-testing tool. Scenarios are written in Python, versioned with the project and run from the CLI or Locust UI. It supports distributed master/worker execution across processes and machines. This distributed mode is only for load generation; we are not introducing application orchestration.

## 3.8 Next.js

Next.js App Router + TypeScript provides the product UI:

- Landing page and URL shortening form.
- List of created links.
- Copy short URL interaction.
- Link details, custom alias and expiry controls.
- Analytics dashboard once analytics is implemented.
- Authentication/account pages in a later milestone.

The frontend must not connect directly to PostgreSQL, Redis or RabbitMQ. It calls the FastAPI HTTP API.

# 4. API contract

All API endpoints are versioned under `/api/v1`. The short redirect route is separate from the API route prefix. Reserve paths such as `/api`, `/health`, `/ready`, `/docs`, `/openapi.json` and static resources so they cannot be used as custom aliases.

## 4.1 Create generated URL

`POST /api/v1/urls`

Request:

```json
{
  "url": "https://example.com/a/long/path?x=1",
  "expires_at": null
}
```

Response `201 Created`:

```json
{
  "code": "aB3dE9kP",
  "short_url": "https://shortcake-api.onrender.com/aB3dE9kP",
  "destination_url": "https://example.com/a/long/path?x=1",
  "expires_at": null,
  "created_at": "2026-11-10T12:00:00Z"
}
```

The actual host is configured through `PUBLIC_SHORT_BASE_URL`, not hard-coded.

## 4.2 Create custom alias

`POST /api/v1/urls`

```json
{
  "url": "https://example.com/docs",
  "custom_alias": "docs"
}
```

If another row already owns `docs`, return `409 Conflict`.

## 4.3 Resolve and redirect

`GET /{code}` and `HEAD /{code}`:

- `302 Found` + `Location` header for an active URL.
- `404 Not Found` for an unknown code.
- `410 Gone` for a known but expired/disabled URL.
- `HEAD` returns the same relevant headers/status without a response body and should not increment ordinary click counts.

Initially send `Cache-Control: no-store` to avoid browser/shared caches hiding click events or retaining stale redirects. We can test HTTP cache policies separately.

## 4.4 Management endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/health` | Process liveness |
| GET | `/ready` | Lightweight required-dependency readiness check |
| GET | `/api/v1/urls` | List links for authenticated user |
| GET | `/api/v1/urls/{code}` | Link metadata, not redirect |
| PATCH | `/api/v1/urls/{code}` | Update destination/expiration if supported |
| DELETE | `/api/v1/urls/{code}` | Disable link owned by caller |
| GET | `/api/v1/urls/{code}/stats` | Aggregate click statistics |

## 4.5 Status-code policy

| Status | Meaning |
|---|---|
| 200 | Metadata/statistics succeeded |
| 201 | URL created |
| 302 | Temporary redirect |
| 400 | Malformed request |
| 401 | Authentication required when enabled |
| 403 | Authenticated but not authorized |

| 500 | Unexpected application error |

# 5. PostgreSQL data model

PostgreSQL is the source of truth. Redis is never authoritative for URL existence or uniqueness.

## 5.1 Tables

- `users`: optional account/ownership table for the authentication milestone.
- `urls`: one row per short link.
- `idempotency_keys`: records creation request identity and canonical response.
- `url_stats`: aggregated click counters.
- `processed_events`: queue-consumer deduplication ledger.
- `click_events`: optional raw click-event history for experiments.

## 5.2 Initial SQL schema

This is the target logical schema. SQLAlchemy models and Alembic migrations will own the actual deployed schema.

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY,
    email TEXT UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE urls (
    code VARCHAR(32) PRIMARY KEY,
    destination_url TEXT NOT NULL,
    owner_id UUID REFERENCES users(id) ON DELETE SET NULL,
    is_custom BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at TIMESTAMPTZ,
    disabled_at TIMESTAMPTZ,
    CONSTRAINT code_not_empty CHECK (length(code) > 0),
    CONSTRAINT expiry_after_creation
        CHECK (expires_at IS NULL OR expires_at > created_at)
);

CREATE INDEX urls_owner_created_idx
    ON urls (owner_id, created_at DESC)
    WHERE owner_id IS NOT NULL;

CREATE INDEX urls_expiry_idx
    ON urls (expires_at)
    WHERE expires_at IS NOT NULL AND disabled_at IS NULL;

CREATE TABLE idempotency_keys (
    principal_key VARCHAR(128) NOT NULL,
    idempotency_key VARCHAR(128) NOT NULL,
    request_hash CHAR(64) NOT NULL,
    response_status INTEGER,
    response_body JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (principal_key, idempotency_key)
);

CREATE INDEX idempotency_expiry_idx
    ON idempotency_keys (expires_at);

CREATE TABLE url_stats (
    code VARCHAR(32) PRIMARY KEY REFERENCES urls(code),
    click_count BIGINT NOT NULL DEFAULT 0,
    last_clicked_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE processed_events (
    event_id UUID PRIMARY KEY,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE click_events (
    event_id UUID PRIMARY KEY,
    code VARCHAR(32) NOT NULL REFERENCES urls(code),
    occurred_at TIMESTAMPTZ NOT NULL,
    referrer_host TEXT,
    user_agent_family TEXT,
    country_code CHAR(2)
);

CREATE INDEX click_events_code_time_idx
    ON click_events (code, occurred_at DESC);
```

`click_events` is optional for the first analytics release. High-volume raw events can grow rapidly. We will define retention and consider date partitioning only after measuring storage/query patterns. Do not store raw IP addresses or full user-agent strings by default; minimize collected data.

## 5.3 Why `code` is the primary key

Redirect lookup is an equality lookup by short code. The primary key creates a unique B-tree index and enforces global uniqueness. Additional indexes are added only for demonstrated query patterns because each index consumes storage and adds write amplification.

## 5.4 Example SQL operations

Lookup:

```sql
SELECT code, destination_url, expires_at, disabled_at
FROM urls
WHERE code = :code;
```

Generated-code insertion:

```sql
INSERT INTO urls (code, destination_url, owner_id, is_custom, expires_at)
VALUES (:code, :destination_url, :owner_id, FALSE, :expires_at)
ON CONFLICT (code) DO NOTHING
RETURNING code;
```

Custom alias insertion uses the same unique constraint. No returned row means the requested alias is already claimed; return 409.

We will inspect plans using `EXPLAIN (ANALYZE, BUFFERS)` in the local lab and compare ORM-generated statements with SQLAlchemy Core/raw SQL alternatives.

# 6. Short-code generation and collision math

## 6.1 Alphabet and keyspace

Use Base62:

```text
0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz
```

Start with eight characters. The keyspace is:

```text
62^8 = 218,340,105,584,896 possible codes
```

Codes are case-sensitive. The allowed path alphabet is URL-safe.

## 6.2 Cryptographic randomness in Python

Use the Python standard library's `secrets` module, not `random`.

```python
import secrets
import string

ALPHABET = string.digits + string.ascii_uppercase + string.ascii_lowercase


def generate_code(length: int = 8) -> str:
    return "".join(secrets.choice(ALPHABET) for _ in range(length))
```

`secrets.choice` uses a cryptographically secure source and avoids the simple modulo-bias mistake of mapping a random byte using `% 62` without rejection sampling. Keep the generator behind an injectable interface so tests can supply a deterministic generator that intentionally repeats a candidate.

## 6.3 Birthday paradox

For a keyspace `M`, the approximate probability of at least one collision after `n` independent generated codes is:

```text
P(collision) ≈ 1 - exp(-n(n-1) / (2M))
```

For one million eight-character codes, the chance of at least one pair collision across the whole set is approximately 0.23%. The chance that the next random candidate collides with one million already-occupied codes is approximately `1,000,000 / 62^8`, or `4.58 × 10^-9`.

These are different quantities. The database unique constraint is still mandatory because correctness cannot depend on probability being small.

## 6.4 Bounded retry algorithm

1. Generate candidate code.
2. Attempt `INSERT ... ON CONFLICT DO NOTHING RETURNING`.
3. If a row returns, creation succeeded.
4. If no row returns, a collision occurred; generate a new candidate.
5. Retry a small bounded number of times (initially five).
6. If all retries fail, return a controlled retryable error and record the failure in normal logs/test output.

Do not place a global lock around code generation. It would serialize unrelated requests.

## 6.5 Compare alternative algorithms later

- Random Base62: selected product default; less predictable, needs collision retry.
- Sequential database ID + Base62: easy and collision-free but enumerable and exposes creation order.
- Snowflake-like IDs + Base62: useful distributed-ID experiment but introduces clock/worker-ID coordination that is unnecessary for the first release.

# 7. Concurrency, duplicate requests and idempotency

There are several distinct concurrency scenarios. They must not be conflated.

## 7.1 Multiple users submit the same destination

Default: each creation gets a different short code. There is deliberately no unique index on `destination_url`.

## 7.2 Multiple users submit the same custom alias

Exactly one request wins. Use a database unique constraint and an atomic insert. Do not use a check-then-insert sequence.

With SQLAlchemy PostgreSQL insert:

```python
from sqlalchemy.dialects.postgresql import insert as pg_insert

stmt = (
    pg_insert(URL)
    .values(
        code=alias,
        destination_url=destination_url,
        owner_id=owner_id,
        is_custom=True,
        expires_at=expires_at,
    )
    .on_conflict_do_nothing(index_elements=[URL.code])
    .returning(URL.code)
)
result = await session.execute(stmt)
created_code = result.scalar_one_or_none()
if created_code is None:
    # Map this to HTTP 409 Conflict.
    raise AliasAlreadyTaken()
```

## 7.3 Same client request retried after a timeout

Use an `Idempotency-Key` request header for URL creation. The key is scoped to a principal/account. For anonymous requests, use a server-issued stable client scope; do not trust a caller-supplied arbitrary principal ID.

Store:

- principal scope;
- idempotency key;
- SHA-256 hash of the normalized request body;
- response status and response body;
- creation and expiration times.

Within one transaction:

1. Attempt to insert the idempotency record with `ON CONFLICT DO NOTHING`.
2. If this request inserted it, create the URL and store its response in that idempotency record.
3. Commit URL and canonical response together.
4. If another request already owns the key, read the existing record after the conflicting insert resolves.
5. Same request hash: return the previously stored status/body.
6. Different request hash: return 409 because the same idempotency key was reused with a different payload.

A seven-day retention period is a starting product policy, not a universal rule. Add cleanup for expired idempotency rows.

## 7.4 Concurrent database sessions

- Each FastAPI request gets its own `AsyncSession`.
- Each RabbitMQ consumer task gets its own `AsyncSession`.
- Never share one `AsyncSession` concurrently across tasks.
- Keep transactions short; do not hold a DB transaction open while waiting for HTTP calls or RabbitMQ network I/O.
- A connection pool bounds concurrent DB connections. Requests above the pool capacity wait for a connection or time out.
- The total maximum connection footprint is roughly `worker_processes × (pool_size + max_overflow)` per application, plus consumers, migrations and other clients.

## 7.5 Database locking and isolation experiments

We will test:

- Read Committed behavior for normal requests.
- `SELECT ... FOR UPDATE` when a workflow truly requires row locking.
- Unique index contention for custom aliases.
- Deadlocks caused by inconsistent lock order.
- Serialization failures if Serializable isolation is tested.
- Connection pool exhaustion and transaction wait time.

Use database constraints for invariants like uniqueness. A Redis distributed lock is not the correctness boundary for URL creation.

## 8.2 Application factory and lifespan

Use FastAPI's lifespan context to create process-level clients once and close them at shutdown. Do not create a database engine, Redis pool or RabbitMQ connection on every request.

Illustrative structure:

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI
from redis.asyncio import Redis
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine

from shortcake.config import settings


@asynccontextmanager
async def lifespan(app: FastAPI):
    engine = create_async_engine(
        settings.database_url,
        pool_size=settings.db_pool_size,
        max_overflow=settings.db_max_overflow,
        pool_timeout=5,
        pool_pre_ping=True,
        pool_recycle=300,
    )
    app.state.session_factory = async_sessionmaker(
        engine, expire_on_commit=False
    )
    app.state.redis = Redis.from_url(
        settings.redis_url,
        decode_responses=True,
        socket_connect_timeout=2,
        socket_timeout=2,
        health_check_interval=30,
        max_connections=settings.redis_max_connections,
    )

    # RabbitMQ publisher/consumer startup is added in the analytics phase.
    try:
        yield
    finally:
        await app.state.redis.aclose()
        await engine.dispose()


app = FastAPI(title="Shortcake API", version="1.0.0", lifespan=lifespan)
```

The example is a scaffold, not the complete application. In the real version, startup must handle dependency connection errors cleanly, close RabbitMQ channels/connections, cancel consumer tasks and drain bounded in-flight work during shutdown.

## 8.3 Database session dependency

```python
from collections.abc import AsyncIterator
from fastapi import Request
from sqlalchemy.ext.asyncio import AsyncSession


async def get_session(request: Request) -> AsyncIterator[AsyncSession]:
    session_factory = request.app.state.session_factory
    async with session_factory() as session:
        yield session
```

Use the dependency in route/service boundaries. Mutating operations explicitly open a transaction with `async with session.begin():`. Read-only routes should avoid unnecessary long transactions.

## 8.4 Middleware and routing order

- CORS with exact allowed frontend origins.
- Request-size limit for JSON bodies (for example 16 KiB for creation requests).
- Request ID/logging middleware if useful; no centralized instrumentation stack.
- `/health` and `/ready` endpoints.
- `/api/v1/...` routers.
- one-segment `/{code}` redirect route, registered after reserved API paths.
- consistent exception handlers.

Do not apply a large JSON body parser to redirect routes. Keep redirect handlers lightweight.

# 10. Redis caching design

## 10.1 Redis client

Use `redis.asyncio` from the `redis` Python package. Create one long-lived client in FastAPI lifespan and reuse its connection pool. Do not connect/disconnect on every request.

## 10.2 Cache key/value

Key:

```text
url:{code}
```

Value JSON:

```json
{
  "code": "aB3dE9kP",
  "destination_url": "https://example.com/article",
  "expires_at": null,
  "disabled": false
}
```

Set a default cache TTL such as 900 seconds (15 minutes) for non-expiring links. For an expiring URL, the Redis TTL must never exceed the remaining URL lifetime. The 15-minute value is an experiment starting point, not a universal optimum.

## 10.3 Cache-aside redirect path

```text
GET /{code}
   |
   v
Redis GET url:{code}
   |
   +-- HIT --> check cached expiry/disabled state --> HTTP 302
   |
   +-- MISS --> query PostgreSQL using code PK
                    |
                    +-- not found --> 404
                    |
                    +-- expired/disabled --> 410
                    |
                    +-- active --> SET Redis with bounded TTL --> HTTP 302
```

PostgreSQL decides whether a link exists and whether the insert/alias is unique. Redis only improves repeat lookups.

## 10.4 Cache invalidation and stale-fill race

On update/disable:

1. Commit the PostgreSQL update.
2. Delete `url:{code}` from Redis.
3. If Redis deletion fails, log it and allow the short TTL to bound stale data.

There is a race worth testing: request A misses cache and reads the old row; request B disables the URL and deletes the cache; then request A writes the old value into Redis after B's deletion. That stale value can remain until TTL expires. For a strict immediate-revocation requirement, use an authoritative status check/version-fencing design or do not cache the status that must be instantly revocable. The initial project accepts a bounded stale window and will document it; we will not claim immediate revocation from cache-aside alone.

## 10.5 Cache stampede

When a popular key expires, many concurrent requests can all miss Redis and query PostgreSQL. Implement in stages:

1. Measure a cold-cache burst without protection.
2. Add process-local single-flight using a per-key `asyncio.Lock`/shared future.
3. Test with multiple FastAPI worker processes; process-local single-flight does not coordinate replicas.
4. Optionally add a short-lived Redis lock: `SET lock:{code} <random-token> NX PX <lease-ms>`.
5. Release only if the token still matches, using a Lua compare-and-delete script.

The lock is an optimization to reduce duplicate work, never the correctness boundary for URL uniqueness.

## 10.6 Custom LRU experiment

Implement a process-local LRU from first principles:

- Dictionary maps key to node.
- Doubly linked list tracks recency.
- `get` moves node to the most-recently-used end.
- `put` updates/inserts and evicts the least-recently-used node when capacity is exceeded.
- TTL metadata is checked on read and/or with a cleanup mechanism.

Expected average complexity: O(1) lookup/update/eviction. Compare this custom cache to a simple `OrderedDict` baseline and Redis. It is local to one process; it is not a replacement for shared Redis.

## 10.7 Redis failure behavior

- Cache healthy: perform cache-aside.
- Cache timed out/unavailable: fall back to PostgreSQL with a bounded DB concurrency limit.
- Do not retry Redis indefinitely.
- If PostgreSQL is also unavailable, return 503.
- Protect the DB pool from being overwhelmed during a Redis outage.

## 10.8 Rate limiting

Implement a fixed-window counter first, then token bucket and sliding-window comparisons. Use Redis Lua to increment and set expiry atomically. A naive separate `INCR` and `EXPIRE` can leave a counter without TTL if the process crashes between commands.

Rate-limit URL creation by IP and later account ID. Redirect rate limits should be more permissive to avoid damaging legitimate shared-link traffic. Configure proxy trust correctly before using forwarded IP headers.

# 11. RabbitMQ and analytics

## 11.1 Why RabbitMQ

RabbitMQ is selected for the first event-processing implementation because we want to learn traditional message-broker mechanics directly:

- Direct/topic/fanout exchanges and routing keys.
- Durable queues and persistent messages.
- Publisher confirms.
- Manual acknowledgements.
- Consumer prefetch.
- Redelivery and retry topology.
- Dead-letter exchanges and queues.
- At-least-once delivery and idempotent consumers.

Kafka/Redpanda is deferred. It becomes useful when we specifically want a retained partitioned event log, replay, multiple independent consumer groups or large streaming pipelines. It is unnecessary to introduce both brokers initially.

## 11.2 Click event schema

```json
{
  "event_id": "c1f6c5d0-5ddc-4e88-bc65-9e1a9a8e2e1f",
  "schema_version": 1,
  "event_type": "url.click",
  "code": "aB3dE9kP",
  "occurred_at": "2026-11-10T12:00:00Z",
  "referrer_host": "example.org",
  "user_agent_family": "Chrome",
  "country_code": "IN"
}
```

Do not include raw IP by default. The event has a stable UUID so duplicate deliveries can be safely detected.

## 11.3 Local topology

```text
FastAPI redirect handler
          |
          v
Publisher (aio-pika, confirms)
          |
          v
Topic exchange: analytics.events
          |
          | routing key: url.click
          v
Durable queue: url.clicks.v1
          |
          v
Consumer (prefetch + manual ACK)
          |
          v
PostgreSQL transaction:
  insert processed_events(event_id)
  if new: increment url_stats
          |
          v
ACK message after COMMIT
```

## 11.4 Redirect latency and event delivery modes

There is a trade-off: waiting for a RabbitMQ publisher confirmation before returning the redirect adds broker/network latency to the critical path. Do not hide this trade-off.

Implement two modes and benchmark them:

**Mode A — best-effort bounded in-process buffer (initial redirect default):**

- Redirect handler places a small event in a bounded `asyncio.Queue` using a non-blocking enqueue.
- A background publisher task sends events to RabbitMQ with publisher confirms.
- If the in-memory buffer is full, the event is dropped and a normal log/counter records the drop; the redirect still succeeds.
- Events in memory may be lost if the process crashes before publishing. This is acceptable only for best-effort analytics.
- Queue size is bounded; never let event objects accumulate without limit.

**Mode B — transactional outbox (durability experiment):**

- Insert an outbox row in the same DB transaction as the event-producing action.
- A publisher worker claims pending rows using `FOR UPDATE SKIP LOCKED`, publishes to RabbitMQ, then marks them published.
- The consumer remains idempotent because publish/ack uncertainty can still cause duplicates.
- This makes analytics more durable but adds a PostgreSQL write to the redirect path. Benchmark the latency and write amplification before adopting it.

Do not use FastAPI `BackgroundTasks` as a durable queue. It is in-process and does not survive crashes.

## 11.5 aio-pika implementation principles

- Use `aio_pika.connect_robust()` for reconnect/recovery behavior.
- Keep a small number of long-lived connections/channels per process; do not open one connection per request.
- Use publisher confirms for broker acceptance.
- Set persistent delivery mode when the queue is durable.
- Use `message_id=event_id` and a content type.
- Consumer uses manual acknowledgement and a bounded prefetch count (start around 50, then benchmark).
- ACK only after the database transaction commits.
- Use bounded retry with delay and a dead-letter queue. Do not immediately requeue every poison message forever.

A lost publisher confirmation can mean the message was accepted but the client did not receive the ACK. Retrying may produce duplicates. Consumer idempotency is therefore mandatory.

## 11.6 Idempotent aggregation transaction

Conceptual SQL:

```sql
BEGIN;

WITH newly_processed AS (
  INSERT INTO processed_events (event_id)
  VALUES (:event_id)
  ON CONFLICT (event_id) DO NOTHING
  RETURNING event_id
)
INSERT INTO url_stats (code, click_count, last_clicked_at, updated_at)
SELECT :code, 1, :occurred_at, now()
FROM newly_processed
ON CONFLICT (code) DO UPDATE
SET click_count = url_stats.click_count + 1,
    last_clicked_at = GREATEST(url_stats.last_clicked_at, EXCLUDED.last_clicked_at),
    updated_at = now();

COMMIT;
```

If the event was already processed, the CTE returns no row and the counter is not incremented. The consumer ACKs the duplicate after it has safely verified/handled it.

The delivery guarantee is **at least once with idempotent processing**, not exactly once.

## 11.7 Public RabbitMQ option

CloudAMQP's current free Little Lemur offer is a shared RabbitMQ broker with a 1-million-message/month quota, up to 20 connections and up to 10,000 queued messages. It is intended for development/small hobby workloads, not load testing or production availability. Re-check the current plan and inactivity policy before relying on it.

For the zero-cost single Render web-service demo, the API process can start a bounded consumer task during FastAPI lifespan (`RUN_CLICK_CONSUMER=true`). Render may spin the service down after inactivity; the broker retains queued messages within its limits, and the consumer reconnects when the API process restarts. This is a pragmatic demo arrangement, not the ideal production worker topology.

Locally, run the consumer as a separate process so API and consumer can be crashed, restarted and benchmarked independently. If the project later moves to paid hosting, split the consumer into its own always-on worker service.

# 12. HTTP, asyncio and networking experiments

## 12.1 FastAPI async behavior

- Async route handlers allow the event loop to switch while awaiting database, Redis and broker I/O.
- `async def` does not make CPU-bound Python code parallel.
- Do not run synchronous blocking DB clients inside async route handlers.
- Do not perform CPU-heavy loops on the event loop.
- Use thread/process offload only when a measured workload requires it.

## 12.2 Uvicorn worker model

Uvicorn can run multiple worker processes. Each worker has its own event loop, memory, Redis client and SQLAlchemy connection pool. More workers are not automatically faster. Benchmark one worker, then two/four where hardware permits, while accounting for multiplied DB pool connections.

For the Render Free demo, start with one worker. Local load experiments may start multiple worker processes manually. We are not adding Kubernetes or an autoscaling/orchestration layer.

## 12.3 Networking topics

Test and document:

- HTTP/1.1 keep-alive versus new TCP connection per request.
- HTTP/2 behavior at the frontend/proxy boundary where available.
- TCP connection establishment and teardown.
- TLS handshake overhead.
- DNS resolution and caching.
- Request/read/write timeouts.
- Slow clients and slow upstream DB/cache operations.
- Backpressure in the event publisher/consumer.
- Reverse-proxy headers and client-IP extraction.
- Connection pool size and saturation.

The redirect handler should avoid unnecessary JSON serialization, blocking I/O and analytics aggregation before sending the 302 response.

# 13. Locust load-testing plan

Locust is the primary load tool. We will write the test scenarios ourselves in Python and keep them in version control. We are not building a new load generator.

## 13.1 What Locust models

- A virtual user is a simulated client executing a task sequence.
- A concurrent user count is not identical to RPS.
- An in-flight request is a request currently waiting for completion.
- An open TCP connection is a transport resource; some user/client configurations reuse connections.
- RPS is the rate at which requests are completed or dispatched; report which interpretation is used.

Locust's normal user/think-time model is primarily closed-loop: a user waits for a response and then proceeds. As latency rises, that user's next request is naturally delayed. Use a realistic think time and describe this behavior. LoadTestShape controls user count/spawn rate, but is not the same thing as an independently scheduled open-arrival model. If we need strict open-loop arrival-rate testing, add a small optional Python asyncio arrival scheduler as a separate experiment; Locust remains the main tool.

## 13.2 Example Locust scenario

```python
# loadtests/locustfile.py
import os
from locust import HttpUser, between, task

SHORT_CODE = os.environ.get("SHORT_CODE", "seedCode1")


class ShortcakeUser(HttpUser):
    wait_time = between(0.2, 1.0)

    def on_start(self):
        self.code = SHORT_CODE

    @task(99)
    def redirect(self):
        with self.client.get(
            f"/{self.code}",
            name="GET /{code}",
            allow_redirects=False,
            catch_response=True,
        ) as response:
            if response.status_code != 302:
                response.failure(f"expected 302, got {response.status_code}")
            elif not response.headers.get("Location"):
                response.failure("missing Location header")

    @task(1)
    def create(self):
        with self.client.post(
            "/api/v1/urls",
            json={"url": "https://example.com/locust-test"},
            name="POST /api/v1/urls",
            catch_response=True,
        ) as response:
            if response.status_code != 201:
                response.failure(f"expected 201, got {response.status_code}")
            else:
                payload = response.json()
                if not payload.get("code"):
                    response.failure("response is missing code")
```

This is a basic mixed-workload example. For dedicated read-only tests, use a separate class/file that only requests pre-seeded codes. Do not let create tasks grow the test database without a cleanup plan. Seed data before the test; do not create one URL in each user's `on_start` unless setup traffic is intentionally part of the experiment.

## 13.3 Locust commands

Local interactive run:

```bash
cd backend
uv run locust -f ../loadtests/locustfile.py --host http://localhost:8000
```

Headless example:

```bash
uv run locust -f ../loadtests/locustfile.py \
  --host http://localhost:8000 \
  --headless -u 1000 -r 50 -t 5m \
  --csv results/redirect-baseline
```

Here `-u` is simulated user count, `-r` is user spawn rate per second, and `-t` is test duration. These do not directly specify target RPS.

## 13.4 Distributed Locust runs

Locust supports a master process and multiple worker processes/machines. The master coordinates the run and aggregates stats; workers execute the users. This is load-generator distribution, not application clustering/orchestration.

Master example:

```bash
uv run locust -f ../loadtests/locustfile.py \
  --master --headless --expect-workers 4 \
  --host http://TARGET_HOST \
  -u 100000 -r 1000 -t 10m
```

Worker on each load-generator machine:

```bash
uv run locust -f ../loadtests/locustfile.py \
  --worker --master-host MASTER_IP
```

Use secured/private networking for Locust master/worker traffic. Do not expose the master interface publicly without access controls. On Windows, Locust's local `--processes` shortcut may be unavailable because it relies on `fork`; use explicitly launched workers or containers instead.

## 13.5 Load ramp

Increase gradually:

1. 100 users — smoke and correctness.
2. 1,000 users — baseline latency/throughput.
3. 10,000 users — pool/socket/cache behavior.
4. 50,000 users — generator and application saturation.
5. 100,000 users — distributed load generation.
6. 1,000,000 virtual users — only with multiple capable load-generator machines and a properly provisioned test target.

A million virtual users is not one million RPS, nor does it guarantee one million simultaneous TCP connections. The load generators must be profiled. Record worker CPU/RAM, network bandwidth, open files/sockets and connection reuse. Do not stress public free-tier endpoints to these levels.

## 13.6 Required scenario catalogue

| Scenario | Workload | Main question |
|---|---|---|
| Redirect hot key | Many users hit one code | Cache hit and hot-key behavior |
| Redirect uniform | Users hit many seeded codes | General cache/database behavior |
| Cold cache | Flush selected keys before run | DB fallback and stampede |
| Create unique | Every create uses a new URL | Write throughput and code allocation |
| Custom alias race | Clients contend for same alias | Exactly one winner |
| Idempotent retry | Many requests share same idempotency key | One logical creation |
| Mixed workload | 99% redirect / 1% create | Representative mixed traffic |
| Redis outage | Cache unavailable | DB fallback and pool protection |
| Queue backlog | Consumer slowed/stopped | Backlog, prefetch and recovery |
| Slow DB | Add DB latency/limit pool | Request queuing and timeout policy |

Use a separate concurrency test (pytest + asyncio) for deterministic race invariants; use Locust for HTTP load and behavior under sustained traffic.

# 14. Automated test strategy

Browser testing is deliberately excluded. API correctness and performance are tested directly.

## 14.1 Unit tests — pytest

Test pure domain logic:

- `generate_code()` output length/alphabet.
- Deterministic collision retries through an injected generator.
- URL scheme validation and length limits.
- Alias syntax/reserved names.
- Expiration computation and timezone handling.
- Cache TTL calculation.
- Rate-limit token math.
- Event schema validation.
- Error-to-HTTP-status mapping.

## 14.2 Async/API integration tests

Use HTTPX with FastAPI's ASGI transport or FastAPI's supported test client. Test the API without deploying it. Tests must cover request validation, API status codes, redirects and error shapes.

## 14.3 Database integration tests

Use a real PostgreSQL test database (Docker Compose or a disposable test database/branch). SQLite is not a substitute for PostgreSQL concurrency tests because locking, types, indexes and `ON CONFLICT` behavior differ.

Test:

- Migrations apply cleanly.
- Generated code uniqueness.
- Concurrent custom alias insert.
- Idempotency transaction/rollback.
- Expiration and disabled state.
- ORM query behavior and SQL plans.
- Transaction isolation and lock contention.

## 14.4 Redis integration tests

Use real Redis in Docker. Test cache hit/miss, TTL, expiry, invalidation, Redis outage, Lua rate-limit atomicity and cache stampede behavior.

## 14.5 RabbitMQ integration tests

Use real RabbitMQ in Docker. Test durable queues, publisher confirms, manual acknowledgements, redelivery, retry routing, dead-letter behavior and duplicate event handling.

## 14.6 Property-based testing — Hypothesis

Generate varied inputs and verify invariants:

- Generated codes always have the right length/alphabet.
- URL validator rejects disallowed schemes.
- Normalization does not change URL semantics unexpectedly.
- Expired URLs never resolve as active.
- Same idempotency key/body returns the canonical response.
- Different body under same idempotency key returns conflict.

Property-based tests complement deterministic examples; they do not prove the cryptographic quality of the random source.

## 14.7 Concurrency matrix

| Scenario | Initial test size | Expected invariant |
|---|---:|---|
| Different destinations | 10,000 concurrent create attempts over a ramp | Independent short codes |
| Same destination | 10,000 | Separate codes under default policy |
| Same custom alias | 10,000 contenders | Exactly one success; rest conflict |
| Forced generator collision | Deterministic repeated candidate | No duplicate DB code; bounded retry |
| Same idempotency key + same payload | 10,000 retries | One logical row and same response |
| Same idempotency key + different payload | Concurrent requests | One canonical payload; others 409 |
| Hot-key cache miss | Thousands of simultaneous requests | Bounded DB lookups after coalescing |
| Concurrent redirects | Ramp to target | Correct destination and bounded failures |

Do deterministic correctness testing at manageable concurrency before stress testing. A test should clean up its generated rows and stop outstanding tasks on failure.

# 18. Deployment plan

The selected public deployment is deliberately simple:

- Next.js → Vercel Hobby.
- FastAPI → Render Free Web Service.
- PostgreSQL → Neon Free.
- Redis → Upstash Free.
- RabbitMQ → CloudAMQP Little Lemur for a small demo, or local RabbitMQ only until the analytics phase is ready.

No Cloudflare dependency is required.

## 18.1 Frontend deployment — Vercel

1. Push the repository to GitHub.
2. Import the repository into Vercel.
3. Set the project root directory to `frontend/`.
4. Configure the supported Node.js/pnpm build settings detected by Vercel.
5. Add `NEXT_PUBLIC_API_BASE_URL`, pointing to the deployed FastAPI API origin.
6. Deploy from the main branch; use preview deployments for frontend changes.

The browser calls the API over HTTPS. The backend CORS allowlist must contain the exact production frontend origin and any explicitly allowed preview origin. Avoid wildcard CORS with credentials.

Vercel Hobby is limited to personal/non-commercial use under its current terms. It is suitable for a personal portfolio/demo; check the terms before commercial use.

## 18.2 Backend deployment — Render

Create a Python Web Service. Set the root directory to `backend/` if using the monorepo.

Suggested build command:

```bash
uv sync --frozen --no-dev
```

Suggested start command:

```bash
uv run --no-sync uvicorn shortcake.main:app --host 0.0.0.0 --port $PORT --workers 1
```

The `--no-sync` flag prevents the start command from trying to modify the deployment environment after the locked production-only sync in the build step. The ASGI import path must match the actual package layout. If the project uses a `src/` layout, install the package through uv so `shortcake.main` is importable.

Important Render Free behavior:

- A free web service spins down after 15 minutes without inbound traffic.
- The next request wakes it; startup can take roughly a minute.
- Free services use an ephemeral filesystem; persistent application files must live in managed databases/object storage, not the container filesystem.
- The free plan grants a limited monthly pool of instance hours (currently 750 hours per workspace/month).
- Free web services cannot scale to multiple instances and are not suitable for production SLAs.
- Free background-worker/one-off-job capabilities are not the basis of this design; see the queue section for the demo's single-service compromise.

The cold start is an accepted limitation for a free portfolio project. A paid always-on web service is needed for consistently low first-request latency.

## 18.3 PostgreSQL — Neon

1. Create a Neon project in a region close to the Render backend.
2. Copy both pooled and direct connection strings.
3. Use pooled `DATABASE_URL` for normal application traffic.
4. Use direct `DIRECT_DATABASE_URL` for Alembic migrations and operations that require a direct/session connection.
5. Convert the libpq-style URI to the SQLAlchemy asyncpg dialect.

Example format for the application URL:

```text
postgresql+asyncpg://USER:PASSWORD@HOST-pooler/DBNAME?ssl=require&prepared_statement_cache_size=0
```

`asyncpg` uses `ssl=require`; it does not accept libpq's `sslmode=require` parameter under that name. For SQLAlchemy's asyncpg dialect, `prepared_statement_cache_size=0` is a conservative compatibility option for transaction-pooler setups if prepared-statement reuse causes errors. Benchmark this setting; if the provider's pooler supports prepared statements correctly and the tests pass, compare the default cache configuration as well.

Use a direct endpoint for migrations, because transaction poolers are intended for application connections and may not support all session-level operations. Keep secrets out of source control.

Neon Free limits currently include 100 compute-hours per project/month, 1 GB storage per project and 5 GB public network transfer per project/month. Compute scales to zero after inactivity; the first query after sleep can incur additional latency. Re-check the live plan because limits change.

## 18.4 Redis — Upstash

1. Create an Upstash Redis database near the backend region.
2. Obtain its TLS/Redis connection URL.
3. Store the URL in Render environment variables as `REDIS_URL`.
4. Connect with `redis.asyncio.from_url()` and configure command/connect timeouts.
5. Keep the same Redis key schema in local and hosted environments.

Upstash Free currently lists 256 MB data size, 500,000 monthly commands and 10 GB monthly bandwidth. The free quota is useful for a small demo but not for load testing. A redirect cache hit still consumes a Redis command; estimate monthly commands before public launch.

## 18.5 RabbitMQ — CloudAMQP option

For a public demo that includes analytics:

1. Create a CloudAMQP Little Lemur free instance.
2. Store the AMQP URL as a Render secret (`AMQP_URL`).
3. Use aio-pika with a robust connection and a small number of long-lived channels.
4. Configure durable exchange/queue and a dead-letter queue.
5. For the single Render Free Web Service, optionally start the click consumer as a background asyncio task from FastAPI lifespan using `RUN_CLICK_CONSUMER=true`.
6. The broker retains messages while the Render service sleeps; the consumer reconnects when the API process wakes.

This embedded consumer is a zero-cost demo compromise, not the ideal long-term deployment topology. Locally, the consumer runs as a separate process/container. On paid hosting, split API and consumer into independent always-on services.

CloudAMQP Little Lemur currently lists a shared broker, up to 100 queues, 10,000 queued messages, 20 connections and 1 million messages per month. It is not a throughput target and has no reason to be used in Locust stress tests.

If the queue is not yet implemented, omit `AMQP_URL` and disable click analytics explicitly. Do not silently lose events while claiming analytics is durable.

## 18.6 Custom domains and redirect URL

Initially:

- Frontend: `https://shortcake.vercel.app` (example only).
- API/redirect host: `https://shortcake-api.onrender.com` (example only).

Set:

- `NEXT_PUBLIC_API_BASE_URL` to the API origin.
- `PUBLIC_SHORT_BASE_URL` to the host that serves `/{code}` redirects.

Later, attach a custom short domain to Render if desired (for example, `s.yourdomain.com`). Ensure DNS and TLS are configured before changing `PUBLIC_SHORT_BASE_URL`. Do not build short links using the frontend origin unless the frontend actually implements and owns the redirect route.

## 18.7 GitHub Actions

CI should:

1. Install the pinned Python version and uv.
2. Run `uv sync --locked --all-groups`.
3. Run Ruff lint and format checks.
4. Run mypy.
5. Run unit/property tests.
6. Start PostgreSQL/Redis/RabbitMQ services for integration tests.
7. Run integration and concurrency tests at controlled scale.
8. Install frontend dependencies with the committed pnpm lockfile.
9. Run Next.js lint/type/build checks.

Deploy only after required checks succeed. Keep provider credentials in deployment secrets, not GitHub logs or source code.

# 20. Security and abuse protection

## 20.1 Destination URL validation

- Parse using Python's `urllib.parse.urlsplit` or Pydantic URL types.
- Allow only `http` and `https` schemes.
- Reject `javascript:`, `data:`, `file:`, `ftp:` and unknown schemes.
- Require a valid hostname.
- Reject embedded username/password unless explicitly supported.
- Enforce a reasonable maximum length (start with 4,096 characters).
- Do not lowercase path/query values or normalize in ways that change destination semantics.
- Validate aliases with a strict pattern such as `[A-Za-z0-9_-]{3,32}`.
- Block reserved route names.

The application does not fetch the destination URL. Therefore a typical SSRF path is not present in the first version. Do not add link-preview fetching without a separate SSRF design that blocks loopback/private/link-local ranges, cloud metadata endpoints, DNS rebinding and redirects to internal addresses.

## 20.2 Abuse

A public URL shortener can be used for phishing, malware distribution and spam. Before unrestricted public creation, implement:

- Per-IP and later per-account creation limits.
- Abuse-report endpoint and administrative disable capability.
- A block/review process for malicious links.
- A visible destination preview or warning policy where appropriate.
- CAPTCHA/account verification if automated abuse becomes material.
- Clear terms and a contact/reporting mechanism.

## 20.3 Proxy headers and client IP

Render sits behind an ingress proxy. Configure Uvicorn/FastAPI proxy-header handling according to the provider's trusted proxy behavior. Do not blindly trust arbitrary client-supplied `X-Forwarded-For` or `Forwarded` values when deriving IP-based limits. Test spoofed-header cases.

## 20.4 Authentication later

Do not invent password cryptography. If accounts are added, use a well-maintained authentication/session approach and Argon2id password hashing through a vetted library such as `pwdlib[argon2]`, or delegate identity to an OIDC provider. Check `owner_id` on every management action; never trust the code alone as proof of ownership.

# 21. Failure behavior and recovery

| Failure | Expected behavior |
|---|---|
| Redis unavailable | Bounded fallback to PostgreSQL; protect DB pool |
| PostgreSQL unavailable | Return 503; never invent a destination |
| RabbitMQ unavailable | Redirect still succeeds in best-effort analytics mode; bounded event buffer may fill/drop and records this |
| Queue consumer crashes | Broker redelivers unacknowledged messages; consumer idempotency prevents double aggregation |
| Render service sleeps | First request may be slow while service wakes; database/Redis/broker remain external |
| Neon scales to zero | First DB query may be slower; pool pre-ping/recycle handles stale pooled connections |
| URL expired | Return 410 and avoid/revalidate stale cache entry |
| URL disabled | Invalidate cache; bounded stale window is documented unless stronger revocation is implemented |
| Random code collision | Bounded retry; DB unique constraint ensures no duplicate code |
| Custom alias collision | Return 409 |
| Same idempotency key/body | Return stored canonical response |
| Same idempotency key/different body | Return 409 |
| Queue message malformed | Reject/route to DLQ; do not retry forever |
| Application shutdown | Stop accepting new work, stop consumer, drain bounded tasks, close Redis/DB/AMQP clients |
| DB pool exhausted | Wait only for configured timeout, return controlled 503/500, observe pool wait time |

All dependency operations need explicit timeouts. Retries must be bounded and should use exponential backoff with jitter where appropriate. Avoid retry storms.

The purpose of the million-user experiment is to measure infrastructure we control. Public free plans have daily/monthly quotas, request limits and small shared resources. # 26. Architecture decisions (ADRs)

| Decision | Choice | Reason |
|---|---|---|
| Backend | FastAPI | Async Python API with Pydantic/OpenAPI integration |
| Python environment | uv | Fast environment/dependency management and committed lockfile |
| ORM | SQLAlchemy 2.x async | Explicit control of sessions, Core/ORM, transactions and query behavior |
| Driver | asyncpg | Async PostgreSQL driver integrated with SQLAlchemy asyncio |
| Migrations | Alembic | Versioned schema changes; no create-all at startup |
| Frontend | Next.js | Full-featured React app and straightforward Vercel deployment |
| Database | PostgreSQL | Constraints, transactions, indexes and MVCC to study |
| Cache | Redis | Shared cache across application processes |
| Broker | RabbitMQ | Queues, ack, confirms, retries and DLQ learning |
| Load testing | Locust | Python-defined HTTP users and distributed load generation |
| Local infra | Docker Compose | Reproducible services without Kubernetes |
| Backend host | Render Free initially | Supports Python/FastAPI deployment; cold-start limitations accepted |
| Frontend host | Vercel Hobby | Simple Next.js deployment for personal/non-commercial demo |
| Analytics delivery initially | Best-effort buffered publish | Keeps broker latency off redirect response; outbox benchmark is later |
| URL uniqueness | PostgreSQL constraint | Atomic correctness under concurrent inserts |
| Duplicate destinations | Independent short links | Separates ownership, expiry and analytics |
| Redirect response | 302 + no-store initially | Avoids permanent browser cache and preserves click visibility |

Any change to these decisions should be recorded in `docs/adr/` with context, decision, alternatives and consequences.

# 28. Final project definition

**Shortcake is a Python-powered URL-shortening platform built with FastAPI, SQLAlchemy 2.x async ORM, PostgreSQL, Redis and RabbitMQ, with a Next.js frontend.** Python dependencies and environments are managed through uv. API and domain tests use pytest/HTTPX/Hypothesis. Performance tests use Locust. Local infrastructure runs through Docker Compose. The personal public demo deploys Next.js to Vercel and FastAPI to Render, with Neon PostgreSQL, Upstash Redis and optionally CloudAMQP RabbitMQ.

We deliberately exclude Cloudflare, Kubernetes, application orchestration, Prometheus, Grafana, OpenTelemetry and browser automation from the initial project. Docker containerization, SQL/database internals, concurrency, Redis algorithms, RabbitMQ delivery semantics, Locust load testing, failure injection and measured optimization remain core parts of the work.

The million-user target is a staged experiment, not an unverified performance claim. We will validate correctness first, profile Locust workers and the application, ramp load gradually and use multiple authorized load-generator machines only when hardware and network capacity permit. A million virtual users is not one million RPS or automatically one million simultaneous TCP connections. Free public hosting is for the demo, never the extreme-load target.
